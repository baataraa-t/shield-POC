Generate SHIELD Signature
APP

SHIELD APIs require the following HTTP headers in every request: Shield-Signature, Timestamp, X-Endpoint-Version, and Site-Id. The Shield-Signatureis also required to retrieve the endpoint.

You can generate the Shield-Signature using the steps below:

1
Use your secret_key to hash the current Unix timestamp (in seconds) using the HMAC SHA256algorithm.

hashed_timestamp = 
hmac_sha256
(timestamp, secret_key)
2
Use the generated hash (from step 1) as the key to hash your Site-Id , again using the HMAC SHA256 algorithm. The generated value is your Shield-Signature , which must be included in the HTTP header.

shield_signature = 
hmac_sha256
(site_id, hashed_timestamp)
You can find your secret key and site ID in the sidebar, or click here to view it.

Sample code for generating SHIELD Signature
public static String getShieldSignature(Long timeStamp, String siteId, String shieldSecretKey) {
    String shieldSignature = "";
    try {
        String timeHash = generateHash(timeStamp.toString(), shieldSecretKey);
        shieldSignature = generateHash(siteId, timeHash);
    } catch (GeneralSecurityException e) {
        e.printStackTrace();
    }
    return shieldSignature;
}

private static String generateHash(String toHash, String secretKey) throws GeneralSecurityException {
    SecretKeySpec keySpec = new SecretKeySpec(secretKey.getBytes(), "HmacSHA256");
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(keySpec);
    byte[] hashBytes = mac.doFinal(toHash.getBytes());
    return Hex.bytesToStringLowercase(hashBytes);
}
Note: A SHIELD Signature is only valid for 5 minutes. If it expires, you must generate a new one using an updated Unix timestamp.

The endpoint is used to concatenate with the API path given, while the version is required to be passed in the headers during the GetDeviceResults API call. We recommend caching the endpoint and version after the first service discovery call.

{
    "endpoint": "https://ap-device-pro.csftr.com",
    "version": 1
}
Refresh your cached endpoint and version to reflect the new one.


Send User ID
APP

Use the sendAttributes function to send device-user related data, such as a user_id, to help SHIELD associate intelligence with a known user. This function accepts two parameters: screenName, which indicates where the function is triggered, and data, which includes the user_id in a key-value pair.

You should send the user_id as soon as it becomes available in the user journey, and again if it changes during the session.

Example: If a user_id is available on the home screen or any post-login screen, send it in your backend API request. If the user logs out and logs back in, send the user_id again to re-associate the session.

Get Device Intelligence
APP

Webhook Implementation
SHIELD uses webhooks to notify your application whenever there are changes in the device profile.

Register a Webhook URL Endpoint
Whenever the device profile changes and the webhook is enabled, SHIELD will send an HTTPS POST request to your endpoint in JSON format. At a minimum, your webhook endpoint must be able to receive and handle an HTTPS POST request. You can register the webhook URL endpoint with the SHIELD team.

Please provide your URL endpoint to the SHIELD team to get started.

Test Your Webhook Endpoint
Before starting the implementation, it can be helpful to test whether the URL is working properly. Remember to test your webhook endpoint regularly, especially:

When the webhook endpoint is first created
After deploying it to a live environment
After making any changes
Parse the Payload
The data in the webhook request sent by SHIELD will be formatted in JSON, as indicated by theContent-Type HTTP header set to application/json .

Verify SHIELD Signature
This step is optional but highly recommended. Since a webhook endpoint is a publicly accessible URL, anyone who obtains the URL could potentially send requests to it, pretending to be SHIELD. To protect against spoofing, device intelligence pushed via webhook from SHIELD will include the following headers:Shield-Signature and Timestamp .

Device Intelligence Response Fields
The device result JSONObject has the following keys:

Key	Description
app_store
Indicates where the app was downloaded from.
device_intelligence
Actionable signals, including device_score and shield_id, along with a set of risk intelligence.
app_tampering
Indicates if the user is using a tampered version of the app.
auto_clicker_enabled
Indicates if the user has enabled an auto-clicker on the device.
debugging
Indicates if the user is trying to debug the application or if the application is modified to allow debugging.
device_score
Numerical indicator of the device’s risk level, ranging from 10 to 120. A lower score indicates higher risk.
hooking
Indicates if the user is altering the behavior of the operating system or apps by intercepting function calls or events.
is_device_masked
Indicates if the user has modified or spoofed device attributes to appear as another device.
is_emulated
Indicates if the app is being used in an emulator.
is_jailbroken
Indicates if the device is jailbroken or rooted.
is_proxy
Indicates if the traffic runs through a VPN, proxy, or other hosting facility.
running_clone_apps
Indicates if the user is using a cloned instance of the app.
running_gps_spoofers
Indicates if the user is running GPS spoofing while using the app.
running_screen_sharing
Indicates if the user’s screen is being remotely accessed or shared to an external display.
running_vpn_spoofers
Indicates if the user is running VPN apps while using the app.
secondary_user
Indicates if the user is operating under a secondary profile on the device’s OS.
shield_id
Unique identifier for the device generated by SHIELD.
suspicious_factory_reset
Indicates if a suspicious factory reset has been performed.
virtual_os
Indicates if the user is operating in a virtual OS environment.
request_payload_tampered
Indicates whether the request payload sent from the SDK to the SHIELD server has been tampered with in transit and should not be trusted.
sus_sdk_conn
Indicates if the sdk network connection is intercepted
device_used_by_more_than_2_users
Indicates if three or more users have used the device in the past 14 days.
is_payload_tampered
Indicates whether device_intelligence has been tampered with in transit and should not be trusted. Available from version 1.5.32 and above.
platform
The platform the user is accessing your app on. Possible values: “Android”, “iOS”, and “Web”.
session_id
A unique identifier of the Browser/App Session assigned by SHIELD.
timestamp
Timestamp of the API response.
user_id
Unique identifier for the user.
version
Version of the API response to ensure backward compatibility when parsing the data.
